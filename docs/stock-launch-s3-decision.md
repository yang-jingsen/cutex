# S3 — opt-in stock launch contract (REFERENCE_ONLY)

## Decision requested

Recommend a Linux-host-only, explicit stock launch adapter inside the existing Cutex app-server lifecycle. Keep **one authoritative native home independent of profile**, one app-server owner per durable Agent, the existing launch claim/recovery boundary, and S2 outbound MCP. Begin with private dummy API-provider profiles and already explicitly adopted durable threads. Do not enable ordinary managed Create, real account switching, production history migration or inbound delivery in this increment. No kernel extension is necessary for that subset. This is a proposed contract, not implementation authorization or a claim that arbitrary current profiles are compatible.

Accepting this packet should explicitly accept native app-server source classification and the restricted authentication subset. If simultaneous existing ChatGPT account profiles with one shared native home are required immediately, the subset is insufficient: investigate a narrow config/auth-location extension or a supported external-auth integration as a separate task. Do not silently select a production credential layout.

## Recommended adapter sequence

1. Explicit opt-in request identifies exact durable ID, reviewed current record/version, supported stock bundle, canonical native home and resolved profile configuration. Reject archived/retired, ambiguous native mappings, incompatible host/backend, unsupported options and unknown ownership. Profile/name/title/cwd never select identity or history. For this first implementation, the native thread must already exist in the designated private home and be explicitly adopted through the existing Human path; no launch-time auto-adoption/import or managed Create.
2. Reuse the current lifecycle ownership claim before spawn. Resolve effective model, reasoning, sandbox and approval from the current durable spec plus explicit supported profile values. Generate a per-launch nonsecret configuration plan; do not overwrite the shared authoritative `config.toml` on each profile launch. Use stock command-line config overrides and supported thread request fields for allowlisted settings. Reject fork-specific options instead of forwarding an arbitrary current profile wholesale.
3. Spawn the exact pinned stock binary with `app-server --listen unix://...` in a private runtime directory using the existing containment/child-handle lifecycle. Native home remains stable. Explicit MCP config names the absolute `cutex-mcp` binary and `env_vars` for only the four S2 launcher variables. Scrub inherited fork config/auth aliases and unrelated credentials. Do not put tokens in argv, model arguments, result JSON or diagnostics. Existing launch authentication remains external to the model.
4. Connect and `thread/resume` the exact native ID, with no second resume owner. No turn is submitted before registration/readiness. Select a fresh runtime ID; the launch plan can carry the expected next generation from the fenced snapshot, but registration and its readback remain authoritative. Confirm exact returned thread, durable mapping, current runtime and generation. Mismatch stops this owned child and reports the actual failed stage; never refresh the confirmation to make it succeed. MCP requests before readiness fail closed. A lost registration/readiness outcome reconciles the same claim/runtime, not another native thread.
5. Use a registration/heartbeat-only mode of the existing host-side bridge, with explicit unregister/owned-child cleanup. Do not start the existing poll/submit/ack worker for stock. This is a bounded mode in an existing owner, not a new daemon or service policy. Registration does not confer project roles; S2 query remains provider-authorized. Outbound sends still have native offline/dedupe limits.
6. Attach the native CLI to the same endpoint with exact thread ID, explicit `--cd`, and stock `-c 'tui.resume_cwd="current"'`. Return leaves the app-server owner running. Approval requests must use the existing native protocol/CLI responder; an unattended request requiring approval must remain pending or fail explicitly, never become `never`. Startup trust/model-migration UI choices must remain explicit, not silently auto-accepted from the test fixture.

The existing manager's app-server schema/journal identity must describe U for this opt-in path, not claim the fork schema hash. Retain raw native source values; Cutex membership/managed status comes from its durable mapping, independently of native analytics labels. Do not edit native metadata to make a stock-created thread resemble a CLI-created one.

## Profile/auth/history boundary

The initial testable mapping is a private dummy API provider, with explicit provider URL/model and environment-key input when applicable, using the same native home across profile changes. Keep configured profile versus effective launch snapshot distinct. Nullable/inherited profile must be resolved explicitly and recorded as provenance; unavailable resolution fails, not a silent global-profile substitute. Restart may change configuration but must preserve durable ID and native ID.

A real API key, OAuth/ChatGPT auth refresh, OS keyring, forced account/workspace selection, and interactive login are different acceptance cases. The `requires_openai_auth=false` fake provider proves none of them. Do not copy production `auth.json`, symlink profile auth files, or refresh shared credentials on behalf of a selected account in this task. For a future single-account stock-native deployment, externally managed login into the one native home is a plausible supported boundary, but it requires separate Human approval and real auth/account tests.

Per-profile homes offer configuration isolation but split native history and mutable native metadata; symlinking only `sessions/` or only sharing SQLite is not an established complete storage contract. Copying rollouts silently forks authority. Therefore retain the shared home for the initial subset and exclude simultaneous incompatible account profiles. A future requirement for both arbitrary isolated current credentials and fully shared native state is the concrete consumer for a narrow config/auth-root extension or proven external-auth adapter; do not introduce that extension now. Never run stock and fork owners concurrently on the same thread. Old-history compatibility/migration requires its own release-state contract before pointing stock at a production home.

Permission conversion must use the existing effective-default helper (`src/runtime/args.rs:197`) without treating an unknown alias as full access. Explicit full access maps to `danger-full-access` plus the explicitly resolved approval policy; read-only/workspace-write remain their respective policies. Stock named permission profiles require an exact supported definition and cannot be inferred from the word “managed.” Reject unsupported remote/container environments and ambiguous policy combinations. S1 OS proofs do not prove all managed turn metadata or current cgroup behavior.

## Prospective implementation scope and acceptance

Proposed writable files: new `src/launch/stock.rs` (pure allowlisted launch/config plan), registration-only mode in `src/app_server/bus_bridge.rs`, opt-in dispatch in `src/cli_app/management_lifecycle.rs`, stock argument branch in `src/runtime/lifecycle.rs`, stock schema selection in `src/app_server/runtime.rs`/`manager.rs` and the existing schema/journal adapter, minimal explicit CLI option in `src/cli/args.rs`, focused tests and this contract. Do not change Agent Management/Bus business semantics, session-store schema, profile identity, global defaults or installed executable resolution. Selection must be explicit on each initial opt-in launch/restart, not persisted as a misleading existing backend enum. If automatic restart cannot recover the exact bundle/config provenance from existing supported binding fields without a new persistent field, stop and return that narrow schema decision rather than claim normal unattended restart.

Subsequent implementation is accepted only with these decisive private executable checks:

- Invoke the actual opt-in lifecycle twice/restart using one adopted native thread: one owner, same native/durable IDs/history, generation changes correctly; concurrent launch and lost readiness do not create another owner/thread. Inject registration/commit failure and show claim-aware recovery with actual owned-process cleanup.
- Two dummy profile configurations sequentially use the same home/thread with different effective settings; shared config and global selected profile remain unchanged. Unsupported auth/account/fork-option cases reject before spawn, and no credential appears in argv/model-visible schema/results. No real credentials are needed for this first gate.
- Actual stock configured MCP query/send after readiness passes S2 authority fences; stale generation rejects. Registration-only bridge performs zero inbound polls/acks and emits no fabricated A4.
- Real Linux PTY same-owner attach/return and an approval-required interaction preserve policy and raw/cooked recovery; full-access and read-only/workspace-write settings are independently observed from stock, with denial where requested. Unknown permission combinations fail closed.
- Actual native source/history readback remains truthful; duplicate native mapping, missing rollout, archived/retired and wrong-home cases reject. No paid model turn or current production history is used.
- Bundle manifest binds U executable, required enabled companions and facade; wrong artifact/config/schema fails before exposure. Exact private child handles own shutdown; inspect no global process arguments.
