# Stock MCP outbound prototype

This source-only prototype adds the `cutex-mcp` stdio entrypoint, not a daemon or an installed integration. It exposes only `query_managed` and `send`. Existing Cutex HTTP handlers remain responsible for authorization, routing, persistence and receipts.

The launcher supplies `CUTEX_AGENT_ID`, positive `CUTEX_RUNTIME_GENERATION`, `CUTEX_AGENT_BUS_URL` (explicit loopback HTTP port) and `CUTEX_AGENT_BUS_TOKEN`. Stock Core supplies `_meta.threadId`. None of these caller-authority fields is accepted in model arguments. The private Human bootstrap credential must never be supplied to the facade. Stock configuration uses its own `CODEX_HOME`; no global profile is changed.

The opt-in MCP headers require a current live registered runtime and an unambiguous, active persistent durable record matching the native thread and runtime generation. Missing, foreign, ephemeral and stale mappings reject. Management uses the validated invocation and existing project/seat authorization; send binds that same durable subject through existing send validation. Unfenced native callers retain their existing behavior. This is an admission fence, not a new cross-store transaction or protection against a malicious same-UID process possessing launcher credentials. Core metadata is trusted at the controlled launcher boundary, not cryptographic attestation.

`query_managed` uses existing action receipts: exact replay retains its snapshot, changed scope under the same action conflicts, and a fresh action performs a fresh authorized query. `send` requires an exact durable target and preserves the requested delivery mode. Ordinary offline targets currently return `target_unavailable` (409). Registered-target success persists a pending message; it does not prove receipt by stock, after-turn ingress, or A4. Native Bus semantic-fingerprint dedupe has a 30-second window. Changed content with the same external message ID may create a distinct message. No content-independent idempotency or exactly-once guarantee is added.

The harness explicitly starts a private stock owner and registers its native threads through existing Cutex APIs. This does not integrate stock into normal managed launch/restart. No kernel patch, identity database, management mutation tool, Task tool, inbound service, history migration or permanent dual-stack policy is introduced.

Reproduce with the fixed stock artifact already present under the S1 root and private debug builds, then run `python3 tests/stock_mcp_boundary.py`. The script refuses an existing task `run/` directory: preserve prior evidence under a distinct owned path before an intentional rerun. It uses private homes, real provider APIs and fake model Responses, with no paid model calls. All build/cache/temp output must stay under the task root. See the companion result for evidence and limits.
